# Data handling

This page documents **where customer data physically lives**, **how it is
protected**, and **how long we keep it**. Everything below is verifiable —
either by reading the open-source code, by inspecting your tenant via the
admin API, or by requesting the attestation pack at `trust@humangr.com`.

## What we store

CoreLink's data surface is intentionally narrow:

| Data class | What it is | Where it lives |
| --- | --- | --- |
| **Content-addressable blobs** | Build artefacts, action outputs, intermediate caches keyed by BLAKE3 / SHA-256 digest | Cloudflare R2 (per-tenant prefix) |
| **Action cache metadata** | Action-result records, REAPI v2 metadata | Cloudflare D1 (plano de controle global compartilhado; primário informado em ENAM) |
| **Hot path / counters** | Short-TTL counters, idempotency keys, rate-limit windows | Cloudflare KV |
| **Per-tenant coordination state** | Tenant-scoped Durable Object instances | Cloudflare Durable Objects |
| **Identity records** | User identities, MFA, session tokens | Clerk (per CoreLink tenant) |
| **Billing records** | Customer ID, subscription ID, invoice references | Stripe; subscription state in the Cloudflare D1 control-plane database |
| **Audit chain** | Append-only Merkle-linked audit events | Cloudflare R2 (audit prefix) + reconcile job in D1 |
| **Telemetry & logs** | Latency histograms, error counts, aggregate metrics — **no customer artefact content** | Sentry (scrubbed error events); the Grafana Cloud exporter is built but not enabled |

We do **not** store: PHI, cardholder data (Stripe holds it), customer email
beyond what's needed for billing notifications, or copies of customer code
outside the CAS surface.

## Residência

> **Onde os dados residem hoje (para ser preciso):** o enum de regiões do
> CoreLink tem seis códigos macro; quatro estão provisionados com um
> bucket de armazenamento na jurisdição correta, e um tenant só pode ser
> fixado (pin) em uma região provisionada — o cadastro rejeita as outras
> duas.

| Pin | Região | Geografia | Status |
| --- | --- | --- | --- |
| `enam` | América do Norte Oriental | Estados Unidos (servido via `iad`) | **Ativo (padrão)** |
| `wnam` | América do Norte Ocidental | Estados Unidos (servido via `iad`) | **Ativo** |
| `weur` | Europa Ocidental | UE (R2 fisicamente na UE; servido via `lhr` / Londres) | **Ativo — os dados R2 da UE permanecem na UE; D1 compartilhado global** |
| `apac` | Ásia-Pacífico | R2 localizado no Japão (`corelink-cas-apac`; servido via `nrt` / Tóquio) | **Ativo desde 2026-08-17** |
| `sam` | América do Sul | Brasil (São Paulo) | **Não provisionado** — não há região da Cloudflare na América do Sul; o cadastro rejeita esse pin |
| `afr` | África | — | **Não provisionado** — sem mapeamento de colo; o cadastro rejeita esse pin |

O que `primary_region` controla:

- **Posicionamento de objetos no R2.** Para as regiões provisionadas, os
  blobs são gravados nos buckets R2 daquela região (buckets nos EUA para
  `wnam`/`enam`; buckets fisicamente na UE para `weur`; o bucket
  localizado em Tóquio `corelink-cas-apac` para `apac`). O guardião de
  residência mapeia `weur`→`lhr` e `apac`→`nrt`, e recusa acesso
  cross-region (`INV-REGION-NO-CROSS-LEAK`). `sam` e `afr` não têm bucket
  para rotear, então o cadastro os rejeita.
- **Posicionamento do D1.** Um banco compartilhado do plano de controle
  global; seu primário é informado atualmente em ENAM sem jurisdição D1.
- **Posicionamento do DO.** Estado de Durable Object fixado por tenant; isto
  não afirma o posicionamento do D1.
- **Semântica de failover.** Durante uma interrupção regional, o caminho
  de failover é documentado por região em
  `specs/_runbooks/RB-DR-DRILL.md`, disponível mediante solicitação via `trust@humangr.com`.
  Para o Brasil especificamente, veja
  [Residência no Brasil & LGPD](/residency/lgpd-brazil) — o Art. 33 §1º
  permite processamento temporário fora da região durante uma emergência
  documentada.

A residência é aplicada por `crates/corelink-privacy-residency-enforcement/`.
O script de verificação específico do Brasil
(`scripts/verify-lgpd-residency.py`) **falha de forma explícita** em vez
de emitir uma atestação verde, porque a residência física brasileira
ainda não está provisionada (não há região da Cloudflare na América do
Sul). Uma API assinada de prova de residência por tenant
(`/v1/tenant/me/residency-proof`) está no roadmap e não é uma capacidade
em que você deva confiar hoje.

## Encryption

### At rest

All persistent storage is encrypted at rest with **AES-256-GCM**:

- **R2 blobs** — Cloudflare-managed SSE (AES-256-GCM) by default.
- **R2 blobs with BYOK** — additional customer-side envelope encryption per
  blob (per-tenant DEK wrapped by the tenant's KMS root key). See
  [BYOK customer-managed keys](/security/byok) for the four supported
  providers (AWS KMS, GCP Cloud KMS, Azure Key Vault, HashiCorp Vault).
- **D1 + KV + DO** — Cloudflare-managed encryption at rest.
- **Backups** — encrypted at rest with the same envelope as the source.

### In flight

- **External traffic:** **TLS 1.2 minimum**, 1.3 negotiated by every client that supports it, with HSTS
  (`max-age=63072000; includeSubDomains; preload`). HTTP/2 + HTTP/3
  available. Cipher suites limited to AEAD (AES-256-GCM, ChaCha20-Poly1305).
- **Edge-to-origin:** mTLS between Cloudflare edge and backing data planes
  per `CTRL-NET-002`.
- **Service-to-service:** internal calls between Workers are routed through
  Cloudflare's encrypted internal fabric.

The full cryptography baseline is in the
[Security overview](/security#cryptography-baseline).

### In use

Worker isolates provide per-request memory isolation (V8 isolate model).
Customer artefact bytes are not held in long-lived memory between requests;
each request gets a fresh isolate.

When BYOK is enabled, **plaintext data encryption keys (DEKs) never leave
the request scope**. They are decrypted from the customer's wrapped form,
used to encrypt or decrypt the blob in-flight, and discarded before the
isolate is recycled.

## Retention

Retention is **driven by data class**, not by a global default:

| Data class | Default retention | Customer-controlled? |
| --- | --- | --- |
| Content-addressable blobs | Customer-configurable; default LRU 90 days | Yes — per-tenant TTL + manual purge |
| Action cache metadata | Mirrors blob TTL | Yes — coupled to blob lifetime |
| Audit chain | **7 years** | No — compliance-driven minimum |
| Identity records (Clerk) | While account active + 30 days post-cancel | Yes — DSR erasure available |
| Billing records (Stripe + control DB) | 7 years (tax / accounting) | No — regulatory requirement |
| Telemetry aggregates (Grafana) | 13 months | No — operational retention |
| Backup snapshots | 35 days rolling | No — operational retention |

### Right to erasure

CoreLink supports GDPR Art. 17 and LGPD Art. 18 erasure requests:

- **Tenant-initiated erasure** via the admin API (`DELETE /v1/tenant/me`)
  triggers a verifiable erasure workflow with cryptographic attestation
  (`INV-DATA-ERASURE-COMPLETE`, `INV-ERASURE-ATTESTATION-SIGNED`).
- **Audit-chain redaction** uses the salt-rotation pattern documented in
  `ADR-S11-003` — the audit record remains for integrity, but the
  PII-bearing claim becomes cryptographically unrecoverable.
- **Backup tombstones** — erasure requests propagate to rolling backups
  within 35 days (the backup window); a tombstone is recorded on day 0
  so a Type II auditor can trace the chain.

The DSR runbooks (`RB-DSR-INTAKE-FAILURE`, `RB-DSR-ERASURE-INCOMPLETE`) cover the
operational side; they are available on request from `trust@humangr.com`.

## Customer data flow (high-level)

```
                ┌─────────────────┐
                │   Your CI / IDE │
                └────────┬────────┘
                         │ TLS 1.2+
                         ▼
       ┌─────────────────────────────────┐
       │ Cloudflare Edge (region-pinned) │
       └────────┬────────────┬───────────┘
                │            │
        ┌───────┘            └─────────┐
        ▼                              ▼
  ┌────────────┐               ┌──────────────┐
  │ Workers    │ in-region     │ Durable Obj  │
  │ (isolate)  │◄──────────────┤ (per-tenant) │
  └─────┬──────┘               └──────────────┘
        │
        ├──► R2 (per-tenant prefix, BYOK envelope if enabled)
        ├──► D1 (plano de controle global compartilhado; primário informado em ENAM)
        ├──► KV (per-tenant namespace, short-TTL only)
        └──► Audit chain (append-only, Merkle-linked)
```

## Verifying it yourself

You don't have to take our word for any of the above. Two options:

1. **Hit the admin API.** Endpoints under `/v1/tenant/me/*` return signed
   attestations of region pin, encryption status, and audit-chain head.
2. **Audit your own data.** Audit-chain inclusion proofs are exportable as
   RFC 6962 proofs you can verify offline. See
   [Audit chain](/security/audit-chain).
