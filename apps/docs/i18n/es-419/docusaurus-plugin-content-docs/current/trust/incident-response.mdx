# Incident response

This page covers the **customer-visible** side of CoreLink's incident
response: how you find out, how fast we tell you, what channels we use, and
where to read the post-mortem.

The internal side — playbooks, runbooks, tabletop schedule, NIST 800-61
alignment — is documented in
`specs/_compliance/IR-TABLETOP-PLAYBOOK.md`, available on request from `trust@humangr.com`.

## Severity definitions

| Severity | Definition | Public communication |
| --- | --- | --- |
| **SEV1** | Customer-impacting outage of a critical surface (API ingress, cache reads, audit chain write path) or a confirmed security incident affecting customer data | Status page within **5 minutes**; email to affected tenants within **30 minutes** |
| **SEV2** | Partial impairment, degraded performance, single-region issue with failover holding | Status page within **15 minutes** if customer-facing; otherwise internal only |
| **SEV3** | Internal issue with no customer impact (e.g., observability blind spot, internal CI break) | Internal only |

## Status page

[hugrl.betteruptime.com](https://hugrl.betteruptime.com) is the **single source of
truth** during an incident. It is operated by **Better Stack**, on
infrastructure separate from the CoreLink production fabric — if CoreLink is
down, the status page is up. It is served from the vendor's own hostname on
purpose: a branded name would have to be served through infrastructure we run, and a status page that shares our fate goes quiet in
exactly the incident it exists to report.

Two components are tracked today:

1. **CoreLink API Health**
2. **CoreLink Container Storage**

This page previously listed eight components — API ingress, CAS read, CAS
write, action cache, audit chain, admin plane, identity and BYOK envelope — and
promised per-region status for each. The status page has never carried them.
The list is corrected here rather than left as an aspiration, because a
component a customer cannot see the state of is not a component that is being
reported on.

### Subscribe

**Programmatic monitoring** — `https://hugrl.betteruptime.com/index.json`
returns the page state as JSON, including `data.attributes.aggregate_state`.
This is the same endpoint the status indicator in our docs header reads.

**Email, SMS, RSS and webhook subscriptions are NOT available today.** This
page previously advertised all four, plus a
`https://hugrl.betteruptime.com/api/v2/summary.json` JSON endpoint and an
enterprise incident-comms distribution address. None of it was real: the
subscription feature is switched off on the status page (`subscribable:
false`), and both `/history.rss` and `/api/v2/summary.json` are
Atlassian-Statuspage paths that this vendor does not serve — they 301 to the
homepage, so a monitoring script polling them would parse HTML and never
report a thing.

If you need to be told rather than to poll, email **support@humangr.com** and
we will add you to the incident list by hand until subscriptions are turned
on.

## Communicating during a SEV1

We follow a deliberate cadence so you can plan around it:

| Time after detection | What you'll see |
| --- | --- |
| ≤ 5 min | Status page flips affected components; initial "Investigating" post |
| ≤ 30 min | Email to affected tenants (security@ + registered tech contact + incident-comms address); initial scope statement |
| Every 30 min | Status page update with the *change since last update* — even if "no change" |
| Until resolved | Continuous updates; on-call commander identified by name in updates |
| ≤ 72h | Public post-mortem **published** on the status page and linked from this Trust Center |
| T+14d | Internal post-mortem review with corrective-action register; summary delta added to the public post-mortem if material |

We follow the templates in
`marketing/launch/CRISIS-COMMS-TEMPLATES.md`:
SEV1 outage, privacy incident, billing bug, BYOK CMK rumor, pentester early
disclosure. The templates exist so we can communicate quickly under
pressure without writing prose from scratch.

## Breach notification

If we confirm a **personal-data breach** under LGPD Art. 46 / GDPR Art. 4(12),
we commit to:

| Authority / party | Window | Reference |
| --- | --- | --- |
| ANPD (Brazil) | **within 72 hours** of awareness | LGPD Art. 33 |
| EU supervisory authority | **within 72 hours** of awareness | GDPR Art. 33 |
| Affected data subjects (high-risk) | **without undue delay** | GDPR Art. 34 |
| Affected enterprise tenant (any incident) | **within 24 hours** of confirmation | DPA §7 |

The 72-hour clock starts at *awareness* — the moment we have a
reasonable degree of certainty that a breach occurred. We have a documented
internal escalation that puts the decision in front of the DPO and Security
Lead within 4 hours of suspicion, well inside the regulatory window.

The breach-notification runbook is
`specs/_runbooks/RB-BREACH-NOTIF.md`;
the tabletop playbook (NIST 800-61 Rev. 2 aligned, six scenarios) is
`specs/_compliance/IR-TABLETOP-PLAYBOOK.md`. Both are available on request from `trust@humangr.com`.

## Reporting an incident *to* us

If you suspect an incident **affecting CoreLink** that we haven't
acknowledged:

| What you saw | Where to send it |
| --- | --- |
| Security vulnerability or active exploit | `security@humangr.com` — see [Security policy](/security/policy) |
| Service outage or degradation not on status page | `support@humangr.com` — we'll page on-call |
| Privacy incident or data-subject concern | `privacy@humangr.com` |
| Pentest finding under coordinated disclosure | `security@humangr.com` — no PGP key is published; send the report over plain email |

24/7 paging is in place across three regions per PagerDuty rotation. A
weekly synthetic page (sent every Monday 14:00 UTC, sustained for 30 days
pre-GA) verifies the rotation actually pages — see
`marketing/launch/STATUS-PAGE-SPEC.md`.
