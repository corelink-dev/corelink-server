### Fixed

- **A refused B-216 receiver read now says which Cloudflare call it was, and the readback keeps its token diagnostic (#1678).** `readback_only` run 36977214852 on the main account recorded only `failed_closed` / `provider_response_rejected`. It had no endpoint, and no token fields at all, because the token diagnostic ran after the inventory read that was refused. Every receiver API helper now attaches an allowlisted record to a failed request: `read_failure` for a GET, `write_failure` otherwise. Each record holds an endpoint label from a closed set (`scripts_list`, `worker_versions`, `worker_deployments`, `worker_subdomain`, `custom_domains`, `zones_list`, `zone_routes`, `service_routes`, `d1_list`, `d1_query`, `token_verify_user`, `account` and the rest), the HTTP status, up to eight numeric Cloudflare error codes, and a message class from a closed set (`authentication`, `permission`, `not_found`, `rate_limited`, `server_error`, `malformed_response`, `transport`, `rejected_without_detail`, `other`). Receipts from `readback_only`, `deploy_once`, `exercise_once` and `disable_workers_dev` carry it. As with #2877, no body, message text, path, ID or token is recorded. `readback_only` now runs the token diagnostic first and on its own, so its result survives a refused inventory read. The receipt also records `token_verifies`: whether either verify endpoint accepted the token at all. The route source carries a table of the Cloudflare permissions each workflow mode needs, so one correctly scoped key can be minted if the staging token lacks them.
