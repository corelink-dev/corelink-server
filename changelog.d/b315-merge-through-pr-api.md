### Fixed

- **The one-command merge (`pre-merge-gate-check.sh --merge`) could not land any PR (B-315).** Its helper built a signed merge commit and pushed it straight to `main`, and branch protection (strict required checks, enforce_admins, linear history) declines every direct push. The helper now lands through the pull-request merge API with `sha=<gated head>` and `merge_method=squash`, keeping the allocation lock, the exact base/main/head capture and revalidation, and the allocator check on the exact `BACKLOG.md` blob bytes. The allocator refuses any backlog fence the lenient parser would skip, an unclosed block, any level-3 item heading not spelled exactly `### B-NNN`, and any `### B-NNN` heading without exactly one block, which it used to read as an item that was never there. It also refuses a head that does not contain current `main` before calling the API. Every git read runs with replacement objects disabled (`GIT_NO_REPLACE_OBJECTS=1`), and a graft file in effect is a refusal, because a local `refs/replace` entry could make the allocator approve a substituted `BACKLOG.md` blob that GitHub would never merge, and a graft could make a head that is behind `main` look up to date. After the merge it proves that the PR is MERGED and that the merge commit's only parent is the captured `main` and its tree is the head's tree; if that proof fails it exits 3 and the gate reports the merge as landed but unproven instead of calling it cosmetic. The merge API pins only the head, so the last read before the merge call re-reads the PR's base and refuses unless it is still `main` at the captured sha; a merge that GitHub nevertheless lands on another base, or that `main` does not contain, exits 4 with a `merged_into_unexpected_base` message and recovery steps. A merge call that did not report success is never reported as a clean merge, and if the PR shows MERGED at a head other than the gated one (another actor merged a head with the same tree after a refused call), the helper exits 5 with `merged_by_other_actor`. The allocation lock is re-checked as the last step before the merge call and right after it; a holder that is a zombie or stopped, or a lock path that is no longer the inode the holder locked, counts as a lost lock. A new hermetic harness runs the real helper against a fake GitHub that declines pushes to `main`, covering the land, dry-run and refusal cases, and checks at every merge call that the allocation lock and the remote lease are still held and that no mutating `gh` call other than the pinned merge is made (attached flag values are parsed, and an unmodelled `gh api` argument form counts as a write). The tests also execute the gate wrapper against that fake. The verifier also checks that the gate wrapper has one helper call site that forwards `--dry-run` and issues no merge of its own. B-315's verify command now starts the interpreter isolated (`python3 -I -S -B`), so a `sitecustomize.py` reached through `PYTHONPATH` cannot run before the verifier; the verifier also re-runs itself isolated when a caller did not, then loads that harness by path from its source bytes (never through the `scripts` package or a bytecode cache) and checks that the `self_test` it calls is the function that source defines. It refuses a checkout that adds `scripts/__init__.py`, `sitecustomize`, `usercustomize` or a `.pth` file. The BASE-owned backlog gate's closure follows the by-path load, so it freezes the harness together with the verifier and, when that gate runs, refuses a PR that edits it. The gate header now names the four checks branch protection requires instead of claiming `required checks = []`.
